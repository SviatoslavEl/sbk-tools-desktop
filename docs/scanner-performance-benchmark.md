# Измерение скорости сканера

`scripts/benchmark_scanner.py` создаёт собственные синтетические PDF и DOCX,
измеряет реальные вызовы обработчика и проверяет изображения / число страниц
результата. Пользовательские документы, рабочая база и существующий кэш не
открываются и не изменяются. Все результаты сохраняются в новых отдельных
каталогах; автоматического удаления нет.

## Варианты запуска

Из корня репозитория, с зависимостями обработчика в окружении Python:

```sh
.venv-scanner/bin/python scripts/benchmark_scanner.py --repeats 3 --pages 10 --label source-local
```

Для исходной версии до изменений передайте `--source-dir /path/to/baseline/scanner-worker/src`.
Сценарий запуска останется прежним, но worker будет импортирован из указанного
каталога. Хеш исходников записывается в отчёт; изменение исходников во время
замера отклоняет результат. Для source-режима можно указать путь к установленному
офисному движку через переменную `SCANDOCUMENT_SOFFICE`; содержимое `.app` не
изменяется.

Для собранного обработчика используется тот же сценарий, но без импорта его
исходников. Параметр `--runtime` указывает каталог, содержащий `resources/`:

```sh
.venv-scanner/bin/python scripts/benchmark_scanner.py \
  --worker /path/to/sbk-scanner-worker \
  --runtime /path/to/scanner-runtime \
  --repeats 3 --pages 10 --label packaged-local
```

На Windows эквивалентный запуск выполняется Python из окружения проекта,
а `--worker` указывает `sbk-scanner-worker.exe`. Никакие права администратора
для измерения не требуются. DOCX требует доступного офисного движка; отсутствие
движка отмечается как ошибка, а не как быстрый успешный результат. Для отдельного
измерения PDF можно передать `--formats pdf`.

Для сравнения сетевого и локального кэша укажите одну и ту же сетевую папку в
`--input-root`, а в `--cache-root` — по очереди сетевую и локальную папку.
В этих папках создаются только новые каталоги с синтетическими данными.
Передавайте одинаковые `--pages`, `--dpi`, `--repeats`, версии обработчика и
офисного движка. Для тяжёлых документов увеличьте `--timeout` (секунды на один
вызов). Большие наборы тестируйте после небольшого пробного запуска.

## Что означает отчёт

- `first-page-cold`: первый просмотр с пустым кэшем приложения.
- `first-page-warm`: повтор той же страницы с тем же кэшем.
- `next-page-cold-raster` / `next-page-warm-raster`: первый и повторный просмотр
  следующей страницы, когда сам документ уже подготовлен.
- `prepare-neighbors` / `prepared-neighbor`: подготовка ещё не просмотренных
  страниц и последующее открытие одной из них.
- `export-after-preview`: экспорт документа с передачей кэша предпросмотра.
- `export-empty-document-cache`: дополнительный экспорт DOCX с другим, пустым
  кэшем преобразования. Кэш операционной системы при этом уже может быть тёплым.

Время включает запуск и завершение нового процесса обработчика, как в текущем
приложении. Проверка готовых изображений / PDF выполняется **после** остановки
таймера. Это не измерение отрисовки интерфейса, пикового расхода памяти или
изолированной скорости одной библиотеки. Кэши ОС и LibreOffice принудительно не
очищаются. `p95` — наблюдаемый процентиль по методу ближайшего ранга; три повтора
дают предварительное сравнение, а не надёжную оценку хвостовых задержек.

Для каждого вызова сохраняются конфигурация, JSONL-события и stderr. Итоговый
`report.json` содержит окружение, отдельные замеры, медиану и наблюдаемый p95.
При ошибке сохраняется частичный отчёт со статусом `failed`; неуспешный вызов
не попадает в успешные замеры. OCR отключён, чтобы сравнение предпросмотра и
конвертации не смешивалось со скоростью распознавания.

## Почему постоянный onefile-кэш пока не включён

Простая замена `--onefile-cache-mode=temporary` на `cached` не внедряется.
В закреплённой Nuitka 2.8.10 существующие распакованные компоненты проверяются
CRC32; общий каталог также требует отдельного решения для конкурентной первой
распаковки. Текущий SHA-256 manifest проверяет внешний исполняемый файл, но не
защищает переиспользуемые распакованные компоненты этим же способом.

Переход на standalone должен одновременно включать размещение зависимостей,
их manifest-проверку, упаковку Windows, подпись Mac и проверки установленного
результата. Нельзя объявлять это завершённым изменением только флага Nuitka.
Другой вариант — длительно живущий изолированный обработчик, но ему нужны
отдельные проверки отмены, аварийного перезапуска и ограничения памяти.

Источник: [код bootstrap Nuitka 2.8.10](https://github.com/Nuitka/Nuitka/blob/2.8.10/nuitka/build/static_src/OnefileBootstrap.c).
